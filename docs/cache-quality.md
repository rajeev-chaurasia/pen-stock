# Cache quality: the hit rate and the false hit rate together

Every LLM gateway publishes a cache hit rate. None of them publish the
false hit rate beside it, and without that the hit rate is not a result.

A semantic cache can be tuned to any hit rate you like by lowering its
similarity threshold. The cost of doing so does not appear in the hit
rate. It appears as answers to questions nobody asked, served fast, with
no error, to a caller who has no way to know. This page measures that
cost on a corpus built so the right answer is known in advance.

It extends `docs/semantic-caching.md`, which reported the same finding
from seven hand picked pairs. The sample here is 257 labelled requests
across 50 question groups, and it confirms the small sample rather than
softening it.

## The short answer

**No. There is no workable threshold.**

The highest cosine similarity between any two *different* questions in
this corpus belongs to a pair of opposites, not to a paraphrase. A
randomly drawn paraphrase outscores a randomly drawn opposite only
**39.0%** of the time, where 50% would mean the distance carries no
information at all. Below 50% means it carries information pointing the
wrong way.

## Ground truth by construction

The usual way to study this is to replay a public dataset of real
questions and judge afterwards whether each hit was correct, normally by
asking a model whether two questions mean the same thing. That is
circular: deciding whether two questions mean the same thing is exactly
the judgement the cache is being tested on, so the study measures the
agreement between two models rather than the correctness of a cache.

`bench/corpus/questions.json` is hand written instead. Every question is
a deliberate transformation of an anchor question, and the
transformation is the label:

| Label | Construction | A hit is |
|---|---|---|
| `repeat` | The anchor resent, byte for byte. | correct, and needs no embedder |
| `paraphrase` | Reworded so the anchor's answer serves it unchanged. | correct |
| `opposite` | One word flipped so it asks the reverse thing. | **a false hit** |
| `unrelated` | A different subject entirely. | a false hit, and the floor |

Nothing has to be judged at scoring time, because the judgement happened
when the question was written. The corpus was **not** generated by a
model, for the same reason: a model's idea of a paraphrase is the thing
under test.

Full schema and rules in `bench/corpus/README.md`.

## Sample size

| | |
|---|---|
| Question groups | 50 |
| Domains | programming 14, operations 13, config 12, general knowledge 11 |
| `repeat` probes | 50 |
| `paraphrase` probes | 100 |
| `opposite` probes | 57 |
| `unrelated` probes | 50 |
| Distinct prompts embedded | 257, once each, reused across every threshold |
| Embedder | `gemini-embedding-001`, 3072 dimensions, the model the gateway uses |
| Answers generated for token accounting | 257, 34430 completion tokens, mean 134 |

The embedded text is what the gateway embeds, not the bare question:
`internal/cache.PromptText` produces `user:<question>` from a real
request body, and the study builds that body and runs it through the
same function. Every request is checked against `cache.Eligible` first,
so nothing is measured on a path the gateway would refuse to cache.

## The exact tier

| Label | n | Hits | Hit rate |
|---|---|---|---|
| repeat | 50 | 50 | 100.0% |
| paraphrase | 100 | 0 | 0.0% |
| opposite | 57 | 0 | 0.0% |
| unrelated | 50 | 0 | 0.0% |

**100% on repeats, by construction.** A repeat is the same bytes, so it
canonicalizes to the same key. It is measured rather than asserted so
that a change to canonicalization shows up here instead of quietly
moving the baseline the semantic tier is judged against.

There is no false hit row for the exact tier because it cannot produce
one. That is the whole argument for it being the default.

## What the distances look like

Cosine similarity of each probe against its own group's anchor.

| Label | n | min | p05 | median | p95 | max | mean |
|---|---|---|---|---|---|---|---|
| repeat | 50 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 |
| paraphrase | 100 | 0.847 | 0.861 | 0.929 | 0.972 | 0.981 | 0.926 |
| **opposite** | 57 | 0.855 | 0.867 | **0.946** | 0.987 | **0.991** | **0.937** |
| unrelated | 50 | 0.497 | 0.507 | 0.547 | 0.588 | 0.592 | 0.548 |
| unrelated anchor pairs | 1225 | 0.444 | 0.523 | 0.577 | 0.687 | 0.834 | 0.588 |

Read the opposite row against the paraphrase row. Its median is higher,
its mean is higher, its maximum is higher, and its minimum is higher.
The opposites are not merely mixed in with the paraphrases. They sit
**above** them on every statistic in the table.

- Paraphrase beats opposite **39.0%** of the time (50% is no signal).
- **63.2%** of opposites score above the median paraphrase.
- Separable by any threshold: **false**. No line divides the two groups.

The unrelated rows are the reassuring part and the only one. Genuinely
different questions land near 0.55, far below anything a threshold would
be set at, so the failure mode is not a cache that answers at random. It
is a cache that is confidently, narrowly wrong.

### The pairs a threshold would have to separate

Highest scoring opposites, which a safe threshold must exclude:

| Cosine | Flip | Anchor | Opposite |
|---|---|---|---|
| 0.991 | should / should not | Should I pass this large struct by reference? | Should I not pass this large struct by reference? |
| 0.987 | less / more | Does ice float because it is less dense than liquid water? | Does ice float because it is more dense than liquid water? |
| 0.987 | raise / lower | Does adding salt to water raise its boiling point? | Does adding salt to water lower its boiling point? |
| 0.986 | safe / unsafe | Is it safe to delete this file while the process is running? | Is it unsafe to delete this file while the process is running? |
| 0.986 | lower / higher | Does water boil at a lower temperature high up a mountain? | Does water boil at a higher temperature high up a mountain? |
| 0.982 | saltier / less salty | Is the Dead Sea saltier than the Mediterranean? | Is the Dead Sea less salty than the Mediterranean? |
| 0.981 | safe / dangerous | Is it safe to delete this file while the process is running? | Is it dangerous to delete this file while the process is running? |
| 0.981 | use / avoid | Should I use a mutex to protect this shared map? | Should I avoid a mutex to protect this shared map? |
| 0.981 | should / should not | Should I use a mutex to protect this shared map? | Should I not use a mutex to protect this shared map? |
| 0.975 | lighter / heavier | Is helium lighter than air? | Is helium heavier than air? |

Lowest scoring paraphrases, which a useful threshold must admit:

| Cosine | Anchor | Paraphrase |
|---|---|---|
| 0.847 | How do I enable sticky sessions on this load balancer? | How can I make this load balancer keep a client on the same backend? |
| 0.849 | How do I remount this filesystem as read-only? | How can I make this already mounted filesystem stop accepting writes? |
| 0.858 | How do I sort a Python list in ascending order? | In Python, how can I arrange the items of a list from lowest to highest? |
| 0.858 | How do I cordon a Kubernetes node? | How can I stop new pods from being scheduled onto this Kubernetes node? |
| 0.861 | How do I mark this configuration field as required? | How can I make startup fail when this configuration field is missing? |

The best paraphrase in the entire corpus scores 0.9806. **Nine opposite
pairs score above it.** A threshold has to sit at or below 0.847 to
catch every paraphrase and above 0.991 to reject every opposite, and
there is no such number.

The mechanism is not subtle. Negating a question changes one short word
out of a dozen, which barely moves a sentence embedding. Rewording a
question changes most of its words, which moves the embedding a lot.
Cosine distance measures how much the wording changed, and this task
needs to know whether the meaning changed. Those are different
questions, and on this corpus they are close to anti-correlated.

Column definitions:

- **Repeat hit** is 100% everywhere because a repeat's vector is its
  anchor's vector. In production the exact tier answers these first and
  the semantic tier is never consulted, so this column is a control, not
  a saving.
- **Paraphrase hit** counts only hits served from the probe's own group.
- **Opposite FALSE** counts every hit. There is no correct hit on an
  opposite.
- **Margin** is paraphrase hit rate minus opposite false hit rate. It is
  negative over most of the range, which means lowering the threshold
  buys more wrong answers than right ones.
- **Wrong tokens** is the share of completion tokens served from cache
  that answered a different question, repeats excluded. See below.

### Reading the curve

There is no crossover. The two curves run together from 0.80 to 0.91,
then the paraphrase curve falls **faster** than the opposite curve. Past
0.91 raising the threshold destroys more good hits than bad ones.

The best margin in the whole sweep is **+5.8 percentage points at 0.91**,
where the tier catches 76% of paraphrases and answers 70.2% of opposite
questions from the cache. That is not a usable operating point. It is
the least bad one.

At **0.95**, the floor Penstock enforces when the tier is switched on,
the tier catches 24% of paraphrases and serves **43.9%** of opposite
questions from the cache. Nearly half the questions whose meaning was
inverted get the un-inverted answer.

At **0.99** the false hit rate finally falls to 1.8%, and the paraphrase
hit rate is 0%. The tier has become safe by never firing.

Nothing between 0.98 and 1.00 rescues it either, and this can be settled
exactly rather than by a finer sweep. The highest scoring paraphrase in
the corpus is 0.9806, so no threshold above that admits a single
paraphrase. Nine opposite pairs score above 0.9806. Both curves are
monotone in the threshold, so the best any threshold in that range can
do is one paraphrase in a hundred against nine opposites in fifty-seven,
and there is nowhere left to look.

### The floor holds

The unrelated column is 0.0% everywhere except one probe at 0.80, and
that one hit was on a *different* group's anchor rather than its own.
The pair responsible is the closest unrelated pair in the corpus at
0.834:

> "How do I enable debug logging in this application?" against
> "How do I make the log level more verbose in this config?"

Two genuinely different configuration questions, one of which would have
been answered with the other's answer.

## Turning the hit rate into money

Every question in the corpus was answered for real by a local model, so
a hit rate can be converted into tokens rather than estimated. A hit
avoids generating that question's own answer, and serves the anchor's
answer instead. Repeats are excluded, because the exact tier answers
those before the semantic tier is consulted and counting them would
credit this tier with savings it did not produce.

| Threshold | Tokens served correctly | Tokens served wrongly | Wrong share |
|---|---|---|---|
| 0.90 | 12598 | 6654 | 34.6% |
| 0.95 | 3543 | 3402 | 49.0% |
| 0.99 | 0 | 160 | 100.0% |

This is the part a hit rate hides. At the shipped floor of 0.95, of
every 100 tokens this tier avoids paying for, **49 of them answered a
question the caller did not ask.** A dashboard would show that as a
saving.

## What is measured

The similarity behaviour of one embedding model, `gemini-embedding-001`,
on 257 short single turn English questions, and the hit and false hit
rates the production `internal/cache` semantic store produces from those
vectors at 20 thresholds.

The hit and miss decisions come from the shipped code, not from a
reimplementation: `cache.NewSemantic`, `cache.NewExact`, `cache.BuildKey`,
`cache.PromptText` and `cache.Eligible` are all called directly. The
command computes cosine itself only for the distribution tables above,
and it cross checks that number against the production store's on every
probe. This run recorded **0 disagreements**; a run with any would refuse
to report.

## What is NOT measured

**Whether any other embedding model does better.** One model was tested.
The failure mode is structural rather than model specific, since one
negating token moves any sentence embedding very little, but this study
does not prove that for models it did not call.

**Multi turn or long prompts.** Every question here is one short user
turn. A real prompt carries a system message, retrieved documents, and
prior turns, all of which are *shared* between an anchor and its
opposite. That would push similarities up and make separation worse, not
better, so these numbers are the optimistic case.

**Whether the paraphrase labels are right.** They were written to be
interchangeable by one person. That is the softest part of the study and
it is the direction that would most change the answer. See below.

**Latency, throughput, or the cost of the embedding call itself.** The
semantic tier adds an embedding round trip to every miss. That is a real
cost and it is not in this study. `bench/README.md` covers latency.

**Anything about the exact tier's real world hit rate.** The repeat rate
here is 100% because the corpus contains exact repeats by construction.
What fraction of production traffic is byte identical is a property of a
workload, not of this cache.

## What would make these numbers wrong

1. **The paraphrases might be too loose.** They were written to be
   answerable by the anchor's answer, but several are quite distant
   rewordings ("How can I make startup fail when this configuration
   field is missing?" for "How do I mark this configuration field as
   required?"). Tighter paraphrases would score higher and lift the
   paraphrase curve. They would not lower the opposite curve, so the
   crossing problem would remain, but the margin at 0.91 would improve.

2. **The opposites might be too strong.** Corpus flips are clean single
   word inversions, which is the worst case for cosine distance. Real
   traffic contains fewer perfectly minimal negations. The false hit
   rate on real traffic would be lower than 43.9% at 0.95, and the point
   stands only because it is not zero and nobody measures it.

3. **A 57 sample opposite arm.** Each percentage point in that column is
   about half a question. The 15.8% at 0.98 is nine questions. Treat
   fine differences between adjacent rows as noise; treat the shape of
   the curve, which is consistent across 20 thresholds, as the result.

4. **One author, one language, one register.** Every question was
   written by one person in plain English. A corpus with more variety in
   phrasing would spread the paraphrase scores wider in both directions.

5. **A cache warmed with 50 entries.** Production caches hold thousands,
   which gives an incoming question far more chances to find a spurious
   neighbour. The one cross group false hit observed here is a hint of
   what a larger store would produce, not a bound on it.

6. **Embeddings are not stable forever.** `gemini-embedding-001` is a
   hosted model that can change under a fixed name. The result file
   records the model, the dimensions and the date, and a rerun that
   disagrees is evidence about the model rather than about this method.

7. **Answers were generated by a 3B local model.** The token counts in
   the money table describe what a small local model produced under a
   160 token cap. A larger model gives longer answers and the absolute
   token numbers move. The **wrong share** is a ratio between two sums
   over the same corpus, so it is far more robust than the totals.

## What Penstock does about it

Unchanged by this study, and now better supported by it:

- The semantic tier is **opt in**. Enabling caching gets the exact tier.
- The configured threshold has a **floor of 0.95**, and this study shows
  that even that floor serves 43.9% of opposite questions. The floor is
  not a safety guarantee. It is a limit on how bad the setting can get.
- Turning it on **logs a warning at startup**.
- `semantic_hit` is its own metric event, separate from `exact_hit`, so
  the tier's firing rate can be watched rather than buried in an
  aggregate.

What would actually fix it is a verification step: send the candidate
hit and the new question to a small model and confirm they are the same
question. That costs an API call, which is the thing the cache exists to
avoid, so it is only worth it when the cached answer is expensive. That
work is not built. This study is what it would have to beat.

## Reproduce

```
export PATH="$HOME/sdk/go/bin:$HOME/sdk/bin:$PATH"

GEMINI_API_KEY=... go run ./cmd/cachestudy -completions
```

Without `-completions` the study skips the token table and runs against
the embedder alone. Without `GEMINI_API_KEY` it exits with a message and
no numbers, rather than inventing a similarity.

Useful flags:

```
-corpus            bench/corpus/questions.json
-min -max -step    sweep bounds, default 0.80 to 0.99 in 0.01
-embed-per-minute  item budget, default 90; the free tier allows 100
-completions-url   default http://127.0.0.1:8100/v1
-out               default bench/results/cache-study-<timestamp>.json
```

The run takes about ten minutes: 257 local completions, then 257
embeddings paced under the free tier's per minute quota.
